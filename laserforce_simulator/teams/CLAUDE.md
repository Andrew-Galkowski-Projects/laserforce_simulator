# teams/

Manages teams, players, and rosters. Serves as the homepage (`/`).

## Models (`teams/models.py`)

**`Team`**: Has exactly 6 `Player` slots — one each of Commander, Heavy, Scout, Medic, Ammo, plus one duplicate role.

**`Player`**: Belongs to a team and has an assigned role. Carries 19 numeric stats (0–100) used as weights by the simulator:

| Category | Fields |
|----------|--------|
| Awareness | `player_awareness`, `game_awareness`, `resource_awareness` |
| Decision-making | `decision_making` |
| Physical | `positioning`, `stamina`, `speed`, `flexibility`, `adaptability` |
| Team | `communication`, `teamwork` |
| Role | `Offensive_synergy`, `defensive_synergy`, `midfield_synergy`, `resupply_synergy`, `resupply_efficiency`, `accuracy`, `survival`, `special_usage` |

`overall_rating` is a `@property` returning the unweighted mean of all 19 stats.

As of **LG-04 player development**, the 19 stat fields are **mutated in place** at each League
`next_season` rollover (a ZenGM-style age curve) and `total_games` is **ticked** there too —
cosmetically: an active-roster player by their real regular-season appearances, a free-agent by
a small random amount (`total_games` is never a develop input). A per-Season immutable snapshot
of the 19 stats + age + overall is persisted as `matches.PlayerSeasonRating`. See the
[`docs/agents/matches/awards-and-development.md`](../../docs/agents/matches/awards-and-development.md) **LG-04 player development + ratings history** section
for the full mechanism.

As of **LG-05 player potential**, `Player.potential` (a nullable `FloatField`, `default=None`;
migration `0012_player_potential.py`) holds a per-Player **projected peak overall** — set at each
League `next_season` rollover (and the founding `league_create` baseline) by LG-05 alongside
development, **mutated in place** like the 19 stats. It is `None`/`default=None` for players outside
any league flow. Details in [`docs/agents/matches/awards-and-development.md`](../../docs/agents/matches/awards-and-development.md) **LG-05 player potential**.

As of **FIN-01 team finance subsystem**, `Player.salary` (a nullable `FloatField`, `default=None`;
migration `0013_player_salary_team_finance.py`) holds a **derived salary** — a deterministic
cap-scaled function of `overall_rating` (`matches.finance.salary_for_overall`), recomputed in place
at the same write sites LG-05 recomputes `potential` (`_write_baseline_ratings` +
`_develop_league_for_new_season`), but **only when the League has `finance_enabled`** — otherwise it
stays `None` (byte-identical to pre-FIN-01). It is **finance-only** (a payroll input — the sum of a
Team's 6 active-roster salaries — for the owner-mood money axis, never a sim input, never edited via
a form) and **derived, not contracted** (no free agency / cap space). `None` for players outside any
finance-enabled flow. Details in [`docs/agents/matches/career-and-finance.md`](../../docs/agents/matches/career-and-finance.md) **FIN-01 team finance
subsystem**.

As of **FIN-04 health budget + injury/availability**, `Player.games_unavailable` (a
`PositiveSmallIntegerField(default=0)`, declared after `salary`; migration
`0014_player_team_health_injury.py`) is the **availability counter**: `> 0` ⇒ the player is out and
unavailable for selection; it is decremented by 1 each fixture the player's Team plays (whether the
player is substituted out or fielded hurt) and **reset to 0 at the League `next_season` rollover**
(in `_develop_league_for_new_season`, over the developing set). There is **no injury-type taxonomy** —
a single integer countdown. The counter only ever moves in a **finance-enabled career League**
(`_is_career_league AND finance_enabled`); outside that gate it stays `0`, byte-identical to
pre-FIN-04. The roll/decrement/roster-resolution mechanics live in
[`docs/agents/matches/career-and-finance.md`](../../docs/agents/matches/career-and-finance.md) **FIN-04 health budget + injury/availability** and
[ADR-0028](../../docs/adr/0028-health-budget-injury-availability.md).

`stat_for_simulation(stat_name, role)` returns `min(int(raw_value * 1.2), 100)` when `role in self.preferred_roles`, otherwise the raw stat value. Invalid `stat_name` values raise `AttributeError` naturally (no explicit guard). Used by `PlayerRoundState` forwarding properties and `BatchSimulator._make_players` to apply the preferred-role boost at simulation time without affecting stored values or `overall_rating`.

`PlayerForm` exposes all 19 stat fields (default 50) with "Set All to Average (50)" and "Set All to Elite (90)" preset buttons. Profile fields (age, started_playing_age, total_games, home_site, height) are also on the form; when adding a new player, the view pre-fills them via `_random_player_profile()`.

`_random_player_profile()` (in `models.py`) returns a dict of randomised profile values drawn from `teams/constants.py`. Age is 16–50; started_playing_age is 16–age; total_games is 0–5000; height is 4'0"–6'10"; home_site is drawn from `LASERFORCE_SITES`; name is drawn from `PLAYER_NAMES`.

`ROLE_STATS` is imported from `matches.sim_helpers.role_constants` — the canonical source for all role-level constants (`ROLE_STATS`, `MAX_LIVES`, `MAX_SHOTS`, `SPECIAL_COST`). Both `teams/models.py` and `sim_helpers/player_state.py` import from there; the duplicate definition that previously lived in `player_state.py` has been removed.

### Team.is_draw_team

`Team.is_draw_team` (`BooleanField(default=False)`, added by **LG-02x-1**) marks a Team that was assembled by a Player-pool draw Tournament's tier-balanced draw (`team_assembly="player_pool"`, named `"random_draw"` before ANG-01f) rather than hand-built. It carries **NO FK to the Tournament / Match** — the durable link from a drawn Team back to its Tournament and its drawn players lives on `matches.TournamentPlayerEntry` (avoiding a `teams → matches` dependency inversion). A drawn Team's `slot_*` FKs hold only the **transient** per-Round role assignment the simulator's `before_round_hook` rewrites in memory each Round; the source of truth for `(player, tier, drawn_team)` is `TournamentPlayerEntry`. Existing rows take `default=False` (no backfill; ADR-0004 disposable-data precedent).

**`Team.roster_errors` relaxation (draw teams only).** Because a drawn Team **references borrowed Players** without `Player.team` ever being reassigned by the draw, the "all players belong to this team" ownership check is **skipped for draw teams**: the `for player, role, slot_name in filled:` belongs-to-team loop (the `player.team_id != self.pk` check) is wrapped in `if not self.is_draw_team:`. **All other validations stay enforced for draw teams** — the all-6-slots-filled check, the **duplicate-player** check, and the **role-distribution** (Scout-only-twice) check. A non-draw Team with a foreign player **still** errors. See [`docs/agents/matches/tournaments-rr-swiss-draw.md`](../../docs/agents/matches/tournaments-rr-swiss-draw.md) `## LG-02x-1 random draw player-pool tournament` and [ADR-0022](../../docs/adr/0022-random-draw-player-pool-tournament.md).

### Team finance fields (FIN-01, FIN-04)

**FIN-01 team finance subsystem** adds five `Team` finance fields (migration
`0013_player_salary_team_finance.py`, all neutral defaults so non-finance Teams are unaffected):
`budget_scouting` / `budget_coaching` / `budget_facilities` (`PositiveSmallIntegerField(default=34)`)
are **ZenGM 1–100 budget levels** (`matches.finance.DEFAULT_LEVEL = 34` is the neutral level —
mid-range cost, zero effect) converted to dollars via `finance.level_to_amount`; `ticket_price` /
`cash` (`FloatField(default=0.0)`) are dollar amounts (`cash` accumulates each Season's profit and
carries across the rollover). **No choices, no validators** — the per-League `finance_enabled` toggle
+ AI defaults keep the levels in band, and `matches.forms.TeamFinancesForm` (ANG-01e, shared by the
HTML POST and `PATCH /api/leagues/<id>/teams/<team_id>/finances/`) rejects out-of-range input
(levels `1..MAX_LEVEL`, `ticket_price >= 0`) instead of clamping it.

**FIN-04 health budget + injury/availability** lands the **fourth budget** — `budget_health`
(`PositiveSmallIntegerField(default=34)`, the same ZenGM 1–100 level on the `finance.DEFAULT_LEVEL = 34`
neutral, migration `0014_player_team_health_injury.py`) — plus `injury_policy`
(`CharField(max_length=16, choices=INJURY_POLICY_CHOICES, default="auto_sub")`, where
`INJURY_POLICY_CHOICES = (("auto_sub", "Auto-substitute"), ("play_hurt", "Play hurt"))`), the
manager-editable per-Team policy for how an injured starter is handled at fixture time (AI teams stay
`"auto_sub"`). `budget_health` is a fourth pure expense line (no revenue side) **and** buys a real
edge: its `finance.health_effect` level scales injury **duration** down (better health spending ⇒
shorter unavailabilities). All four budgets now buy a gameplay edge — **facilities** feeds the
revenue/attendance side (FIN-01), **coaching** feeds LG-04 development (FIN-02), **scouting** feeds
LG-05 potential (FIN-03), **health** shortens injuries (FIN-04). Details in
[`docs/agents/matches/career-and-finance.md`](../../docs/agents/matches/career-and-finance.md) **FIN-01 team finance subsystem** /
**FIN-04 health budget + injury/availability** and
[ADR-0027](../../docs/adr/0027-team-finance-subsystem.md) / [ADR-0028](../../docs/adr/0028-health-budget-injury-availability.md).

### Team.manager (UX-01) — and the naming hazard

`Team.manager` (**UX-01**, migration `0015_team_manager.py`) is the **Account** a Team belongs to:
`ForeignKey(settings.AUTH_USER_MODEL, null=True, blank=True, on_delete=models.SET_NULL,
related_name="teams")`. `Team` is one of the five **Ownership roots** — it has no parent FK, so it is
*always* a root and carries the FK directly; its `Player`s are derived rows and have **no `manager`
column** (one FK per aggregate — `Player` resolves its Manager by traversing `player.team`).

`manager IS NULL` is an **Unmanaged row**: readable **and** writable by any authenticated Account,
and listed to all of them. `SET_NULL` means deleting an Account in Admin **demotes** its Teams to
Unmanaged rather than cascading their Matches and events away. `_generate_teams` gained a
keyword-only `manager=None` parameter (appended last, so existing callers are source-compatible; since
ANG-01a it lives in `teams/services.py`, re-exported from `teams.views`), and
`team_create` stamps `manager_or_none(request)` via `form.save(commit=False)`. `team_list` and
`player_list` are filtered through `accounts.permissions.owned_queryset` (`path="team"` for Players),
and every `get_object_or_404` in `teams/views.py` became `get_owned_or_404(..., request, ...)`.

The global `"Free Agents"` singleton (`get_free_agents_team()`) is **deliberately never stamped** — it
is a cross-Account shared pool, and stamping it would let the first Account to run `generate_players`
with `num_teams == 0` capture it permanently and 404 it for everyone else. `_generate_free_agents`
and `get_free_agents_team()` keep their signatures verbatim.

> ### ⚠️ Naming hazard: `Team.manager` is NOT `Team.managed_in_leagues`
>
> | Name | What it is | Direction |
> |---|---|---|
> | `Team.manager` | **NEW (UX-01).** The FK above — the **Account** that owns this Team. | Team → Account |
> | `Team.managed_in_leagues` | **PRE-EXISTING.** The reverse accessor of `League.current_team` — the Leagues in which this Team is the manager's **career seat**. | Team → Leagues |
>
> Near-homographs pointing in **opposite directions** at unrelated concepts. `Team.manager` is set on
> **every** generated AI Team, so it is emphatically *not* the career seat; the career seat is
> `League.current_team` (and its reverse, `managed_in_leagues`).
>
> Second hazard: the **Manager** (this Account FK) is **not** the **Owner** — that is the fictional
> boss of [ADR-0026](../../docs/adr/0026-manager-firing-owner-mood.md) (`OwnerEvaluation`,
> `owner_mood.py`), never a login and deliberately unrenamed. Do not introduce the word "owner" for
> an Account.

See [`../accounts/CLAUDE.md`](../accounts/CLAUDE.md) for the permission seam and the traversal table,
and [ADR-0038](../../docs/adr/0038-accounts-and-uniform-manager-ownership.md).

### Player.self_insert_of (UX-02) — the Self-insert link

**UX-02** lets an Account link one existing Player as its **Self-insert** (GLOSSARY.md). The FK lives
on the Account — `accounts.User.self_insert = OneToOneField("teams.Player", null=True, blank=True,
on_delete=SET_NULL, related_name="self_insert_of")` (migration `accounts/0002_user_self_insert.py`)
— so **`Player` gains no column and `teams` gains no migration**; it only gets the reverse accessor
`player.self_insert_of`. That accessor raises `RelatedObjectDoesNotExist` when unlinked and
**production code never reads it** — go through `accounts.self_insert.get_self_insert(user)` /
`is_self_insert_eligible(player, user)` instead. It is a **link, not a copy**: linking never moves,
enrols or re-rosters the Player, never touches a `slot_*` FK, and changes nothing the simulator sees.
Deleting the Player (or its Team, which cascades it) leaves the Account with no Self-insert.

Eligibility is **strict**: only a Player whose `team.manager_id == user.pk`. Players on an
**Unmanaged** Team (including the never-stamped global "Free Agents" singleton) are not linkable. If
the Player later leaves the Account's ownership (Team demoted to Unmanaged, Player moved to "Free
Agents"), the link has **drifted** — `get_self_insert` returns `None` at read time with no write, and
the link reappears if ownership returns.

**Sandbox surfaces:**

- `templates/teams/player_detail.html` (`player_detail`, `/teams/<team_id>/player/<player_id>/`) — a
  POST form in the identity card directly under the Team name: *This is me*
  (`self-insert-link-form` / `self-insert-link-button`, posting to `self_insert_link`) when `team` is
  managed by this Account and the Player is not already the Self-insert; *Unlink*
  (`self-insert-unlink-form` / `self-insert-unlink-button`, posting to `self_insert_unlink`) when it
  is; nothing on an Unmanaged Team. **No view change.** This page is also the fixed target of the
  topnav **"My player"** link (`account-my-player-link`).
- The **"You" badge** (`{% load self_insert_tags %}` … `{% you_badge player.id %}`, rendering the
  `you-badge` span) follows every server-rendered Player name on: `player_detail.html` (the `<h3>`),
  `team_detail.html` (active roster + bench), `player_list.html` (`/players/`),
  `player_career_stats.html` (the `<h1>`) and `player_delete.html`. Not on `<title>`, the avatar
  initial, `<option>` text or form widgets (`team_slots_form.html`). No `teams` view changed.

Full contract in [`../accounts/CLAUDE.md`](../accounts/CLAUDE.md) **Self-insert (UX-02)**.

## REST API (`teams/api_views.py`, `teams/filters.py`, `teams/serializers.py`, `teams/services.py`)

**ANG-01a** turned this into a read/write API. Project-wide conventions (envelope, error codes,
pagination, Form-bound writes, `django-filter`) live in the `laserforce_simulator/api/` package and
[ADR-0039](../../docs/adr/0039-rest-api-envelope-and-form-bound-writes.md) — see **API conventions**
in [`matches/CLAUDE.md`](../matches/CLAUDE.md). Every response here is
`{"data": ..., "meta": {...}}` / `{"errors": [{code, message, field}], "meta": {}}`. Serializers are
**output-only**; every write binds the same Django `Form` the HTML view binds. Ownership:
`get_queryset()` is `owned_queryset(...)` (Players via `path="team"`), so another Account's Team /
Player is **404 on every read and write**, and the row is left unchanged.

**405s (locked):** PUT / DELETE `/api/teams/<pk>/` (**there is no team DELETE**), GET on `slots/` and
`players/`, POST / PUT `/api/players/`, PUT `/api/players/<pk>/`, GET on `generate/` and `import/`,
POST on `import/template/`. The three `detail=False` actions register before the detail route, so
`generate` / `import` never resolve as a `pk` (the ANG-01b `head-to-head` / `benchmarks` actions
likewise).

**Analytics reads (ANG-01b).** Model instances are flattened to refs — `team_ref = {id, name}`,
`player_ref = {id, name, team: team_ref | null}`; builder output is passed through verbatim
(including `detail_list[*].detail_url`, an HTML path). Query params are **strict** param Forms bound
via `plain_form_data(Form, request.query_params)` + `validate_form_or_raise` (the HTML pages keep their
lenient parsing): missing id ⇒ `required`, non-int / bad date ⇒ `invalid`, id < 1 / negative
`threshold` ⇒ `min_value`, bad `provenance` / `role` / `display` ⇒ `invalid_choice`, the same id twice
⇒ `invalid` with `field` null (checked **before** the lookup, so an unknown id repeated is 400, not
404). Rows then resolve through `get_owned_or_404` (head-to-head) or `get_object()` (career) — unknown
/ cross-Account ⇒ 404. Defaults: `provenance` "all", `role` null, `threshold` 5, `display` "mean".
`BenchmarkParamsForm` lives in **`teams/api_forms.py`** (new). Known gap (PLAN.md Deferred Items): the
head-to-head round sets and the career page's own round set are not ownership-filtered. The
**benchmark population** (the standalone page and the career overlay) **is**, since UXP-14 — see
**HX-02 role benchmarks → Ownership scope**.

**Write rules worth knowing.** A slot holding a player not on this Team (including another
Account's) ⇒ 400 `invalid_choice`, `field: "slot_<x>"`, and the message **never names** the foreign
player. Out-of-range stats ⇒ 400 `max_value` / `min_value` on that field. `GenerateLeagueForm.clean`'s
cross-field error ⇒ `field: null`. Free-agent mode (`num_teams="0"`) returns `created_teams: []`,
`free_agent_count: N`, still 201. Roster parse / DB-collision errors map one-per-`RowError` to
`{"code": "roster_invalid", "message": e.message, "field": "row:<n>:<column>" | "row:<n>"}` via
`roster_import_errors_to_envelope` (`row:0` = file-level / header errors); the import is atomic, so
any error writes nothing.

**Filters + ordering** (`teams/filters.py`, list only — detail / write lookups ignore query params,
so the Free Agents Team is still reachable by id):

- `TeamFilterSet`: `name` (icontains); `include_free_agents` (boolean). **By default the list excludes
  every free-agent pool Team** — the global "Free Agents" Team and per-League pools, exactly
  `Team.objects.regular()`, matching the HTML `team_list`; `?include_free_agents=true` includes them.
  Ordering: `name` (default), `created_date`, `wins`, `losses`, `id`; tiebreak `id`.
- `PlayerFilterSet`: `team` (id; a foreign / nonexistent id ⇒ 200 empty, no existence leak; `team=abc`
  ⇒ 400), `name` (icontains). Ordering keys = exactly the 23 LG-00c `_SORT_KEYS` (public
  `offensive_synergy` → ORM `Offensive_synergy`, `team` → `team__name`, `overall_rating` → the
  `overall_rating_db` annotation from `annotate_overall_rating`); `preferred_roles` and the raw
  `Offensive_synergy` are not valid terms (silently dropped). Default `team__name, name`; tiebreak
  `name, id`. `PlayerSerializer` output is unchanged (no `overall_rating` field).

## HX-01 career stats

A per-player career page aggregating `PlayerRoundState` across every round the player appears in, served at `GET /players/<int:player_id>/stats/` (URL name `player_career_stats`, view `teams/views.py::player_career_stats`). The URL deliberately sits at the flat `/players/<pid>/` root — **not** nested under `/teams/<id>/` — so a future cross-team-history feature does not need to break URLs even though every `Player.team` FK is single-CASCADE today.

**URL include.** A NEW URL file `teams/player_urls.py` (`app_name = None` — explicit; reverse stays the bare `'player_career_stats'`, no namespace prefix) is included from `laserforce_simulator/urls.py` as `path("players/", include("teams.player_urls"))` placed **above** the `path("", include("teams.urls"))` homepage catch-all. **Order matters** — Django resolves top-to-bottom, so the include must sit above the `""` catch-all or the homepage will shadow it.

**Pure aggregation module.** `teams/career_stats.py` is the algorithmic seam — **pure Python, no Django imports, no ORM, no RNG, no I/O** (frozen import allowlist: `typing`, `collections`, optional `math`, and `SPECIAL_COST` from `matches.sim_helpers.role_constants`). The Tests agent pins this with a "no Django imports leaked" defensive check mirroring the RES-04 / RV-03 precedent. The module's public surface is four functions:

- `summarize(rounds: Iterable[Mapping]) -> dict` — career totals across every round, returning **exactly** six keys `{games, avg_points, tag_ratio, avg_survival_ticks, avg_accuracy_pct, avg_sp_earned}` (empty input ⇒ `games=0` and every other key `0.0`, no division by zero).
- `summarize_by_role(rounds) -> list[dict]` — per-role breakdown, one entry per role **actually played**, in the locked order Commander/Heavy/Scout/Medic/Ammo (roles not played are omitted; empty input ⇒ `[]`).
- `points_trend(rounds, window=10) -> list[list]` — rolling-mean trend of `points_scored`, returning `[[round_idx, mean_points], …]` with `round_idx` 1-based, sorted ascending by `(date_played, game_round_id)` tiebreaker, partial trailing window for rounds 1..9 and full 10-window for rounds 10+. The `list[list]` (not `list[tuple]`) shape makes `json_script` serialisation trivial.
- `rolling_mean(values: list[float], window=10) -> list[float]` — the pure helper used internally by `points_trend`, exported so tests can pin it directly without depending on `points_trend` ordering.

**Formulas (frozen, sum/sum where statistically required).** `Tag ratio` = `sum(tags_made) / max(sum(times_tagged), 1)` — sum/sum, **not** mean-of-per-round-ratios; pinned by `test_tag_ratio_is_sum_over_sum_not_mean_of_ratios` against the deliberately-asymmetric `10/1` vs `0/100` two-round case where mean-of-ratios would yield `5.0` and sum/sum yields ≈ `0.099`. `Avg survival ticks` = `mean(min(was_eliminated_at, 1800))` — the cap is TIME-01's `TICKS_PER_ROUND = 1800`, so `SURVIVED_SENTINEL = 1801` contributes 1800 (the `÷2` tick → second conversion is applied at the **template** layer only via the existing `team_extras.div` filter, TIME-01). `Avg accuracy` = `sum(tags_made) / max(sum(tags_made + shots_missed), 1) × 100`. `Avg SP earned` = `mean(final_special + SPECIAL_COST.get(role, 0) × specials_used)` — the `.get` fallback contributes **0** for Heavy (which has no `SPECIAL_COST` entry), pinned by `test_avg_sp_earned_mixed_roles_includes_heavy_fallback`.

**Round-dict crossing the view ↔ pure-module seam.** The view assembles a list of plain-dict rounds and hands the list to the pure functions; each dict carries **exactly** ten frozen keys `{role, points_scored, tags_made, times_tagged, shots_missed, final_special, specials_used, was_eliminated_at, date_played, game_round_id}` — no extras, no aliases. The pure module never sees a Django model, `PlayerRoundState`, `GameRound`, `select_related`, or any ORM type.

**View.** `player_career_stats(request, player_id)` runs `get_object_or_404(Player, pk=player_id)` (→ 404 on missing) and **exactly one** ORM query — `PlayerRoundState.objects.filter(player=player).select_related("game_round").order_by("game_round__date_played", "game_round_id")` — then assembles the round-dict list, calls `summarize` / `summarize_by_role` / `points_trend`, and renders `templates/teams/player_career_stats.html` with **six** frozen context keys: `player`, `total_rounds`, `career`, `per_role`, `trend`, `has_rounds` (with `has_rounds = total_rounds > 0`). The view is read-only; no `@require_GET` decorator is contracted (Django views accept any method by default and the view is non-destructive).

**Template surface.** `templates/teams/player_career_stats.html` extends `base.html`, `{% load team_extras %}` for the `div` filter, and renders three surfaces gated on `has_rounds`: a 6-column career-totals row (DOM id `career-totals-table`), the per-role table (DOM id `career-per-role-table`, `|title`-cased role labels), and a Chart.js dashed-line rolling-10 trend chart (canvas DOM id `points-trend-chart`, json_script id `trend-data`, dataset label `"Avg points (rolling 10)"`, x-axis title `"Round number"`, y-axis title `"Avg points (rolling 10)"`, `pointRadius: 2`). The empty branch renders a notice (DOM id `career-no-rounds-notice`) containing the substring `"No rounds played yet"` in place of the three surfaces; tests pin via substring match. Formatting is locked: avg points `|floatformat:1`, tag ratio `|floatformat:2`, survival `|div:2|floatformat:0` + `s` suffix (the `div` filter is the same `teams/templatetags/team_extras.py::div` used elsewhere for tick → seconds at the template layer, TIME-01), accuracy `|floatformat:0` + `%`, SP earned `|floatformat:1`, role labels `|title`-cased so `"commander"` renders as `"Commander"`.

**Entry point.** A single `"Career stats"` anchor in `templates/teams/player_detail.html` reversing `{% url 'player_career_stats' player.id %}`. Tests pin via substring `"Career stats"` in the rendered `/teams/<team_id>/player/<player_id>/` response body. **HX-04 addition:** the career page itself gains an outgoing `player-h2h-link` "Head-to-head" anchor in its header (sibling to the existing `role-benchmarks-link`) reversing `{% url 'player_head_to_head' %}?player_a={{ player.id }}` — the single locked entry point for the HX-04 Player head-to-head record view (see [`docs/agents/matches/round-views-and-analytics.md`](../../docs/agents/matches/round-views-and-analytics.md) `## HX-04 player head-to-head`).

**Determinism / scope.** **Read-only view** — no RNG, no simulation, no `_flush_to_db` touch, no SIM-07 / SIM-08 contract interaction, no Score Calibration re-baseline obligation. **No model change, no migration**, no ADR (reversible: pure read-only view + pure aggregation module), no GLOSSARY.md edit (the **Tag ratio** term was added inline during the grilling session that produced this contract). ## HX-02 role benchmarks

Per-`(Role, Stat)` **Role benchmark** statistics (mean / median / p25 / p75 / p90 / n) and per-player **Percentile rank** (both terms in [GLOSSARY.md](../../GLOSSARY.md)) computed over the population of every player's career-average-when-playing-that-Role across the `PlayerRoundState` rows of every Round the requesting Account may see (**UXP-14** — see **Ownership scope** below). Surfaced two ways: a standalone per-role page at `GET /players/benchmarks/` (URL name `role_benchmarks`, view `teams/views.py::role_benchmarks`) rendering one table per role across all 12 `STAT_KEYS`, **plus** an additive extension to the HX-01 per-player career page that decorates each per-role stat cell with mean/median/delta/percentile/n.

**URL include.** The new entry sits at the top of `teams/player_urls.py` — listed **FIRST**, above the existing `<int:player_id>/stats/` HX-01 route — so the `/players/benchmarks/` literal does not get shadowed by the `<int:player_id>` capture group. The HX-01 outer include (`path("players/", include("teams.player_urls"))` placed above the homepage catch-all in `laserforce_simulator/urls.py`) is reused unchanged.

**Pure aggregation module.** `teams/role_benchmarks.py` is the algorithmic seam — **pure Python, no Django imports, no ORM, no RNG, no I/O** (frozen import allowlist: `bisect`, `statistics`, `collections.defaultdict`, `typing.Iterable`/`Mapping`). The "no Django imports leaked" defensive check mirrors the HX-01 / RES-04 / RV-03 precedent. Module-level constants: `STAT_KEYS` (12-tuple in frozen order — `points_scored, tags_made, times_tagged, accuracy, shots_missed, final_special, specials_used, mvp, final_lives, resupplies_given, missiles_landed, follow_up_shots, reaction_shots, combo_resupply_count`), `RATIO_STATS = frozenset({"accuracy"})`, `MVP_DERIVED_STATS = frozenset({"mvp"})`, `ROLES = ("commander", "heavy", "scout", "medic", "ammo")`. The public surface is six functions: `build_role_populations(rounds, *, threshold=0)`, `apply_threshold(populations, *, threshold)`, `summarize_population(values)`, `percentile_for(values, x)`, `compute_role_benchmarks(rounds, *, threshold=0)`, and `player_position(populations, role, stat, x)`.

**Aggregation rule.** Per-round mean for every stat in `STAT_KEYS` **except** `accuracy`, which uses the Tag-ratio-style sum/sum shape `sum(tags_made) / max(sum(tags_made + shots_missed), 1)` per-player within that role's subset (mirroring the HX-01 `Avg accuracy` formula). The view-side pre-computed `mvp` (from `calculate_mvp`) is treated as a per-round value and rolled up with the same per-round-mean rule as every other counter — the seam carries `mvp` already-computed so the pure module never touches MVP weight logic.

**Subject-inclusion policy.** Mean / median / percentile are computed over the FULL population INCLUDING the subject, so the standalone-page row and the HX-01-overlay cell for the same player are **guaranteed identical** (no off-by-one between an "all players" framing on the standalone page and an "all other players" framing on the per-player overlay). Population maximum maps to `100.0`. Below-threshold subjects (`player_position` returns `qualified=False`) render `— (need N+ rounds)` in the view, substituting the active `threshold` value.

**Query params.** `?threshold=<int>` (default `5`, clamped `≥ 0` — negatives, non-int strings, and missing values fall back to `5`) and `?display=mean|median` (default `mean` — any other value falls back to `mean`). Threshold gates *visibility* per `(role, stat)` row, not the underlying cached samples.

**HX-01 → STAT_KEYS overlay mapping (v1).** Only `avg_points → points_scored` and `avg_accuracy_pct → accuracy` map onto a STAT_KEYS entry and so receive benchmark cells on the HX-01 page; the other three HX-01 display stats (`tag_ratio`, `avg_survival_ticks`, `avg_sp_earned`) render `<td class="benchmark-na">—</td>` until **HX-01b** lands (which extends the per-role table to the full 12-row set so every benchmarked stat surfaces its overlay). `tag_ratio` / `avg_survival_ticks` / `avg_sp_earned` remain HX-01-only derived stats — they are not in `STAT_KEYS` and HX-02 does not benchmark them.

**Round-dict crossing the view ↔ pure-module seam.** A strict **18-key SUPERSET** of HX-01's 10-key dict — additive, with HX-01 signatures unchanged: the 10 HX-01 keys (`role, points_scored, tags_made, times_tagged, shots_missed, final_special, specials_used, was_eliminated_at, date_played, game_round_id`) plus **6 HX-02 raw counters** (`final_lives, resupplies_given, missiles_landed, follow_up_shots, reaction_shots, combo_resupply_count`, all int) plus **2 view-side pre-computed floats** (`mvp` via `PlayerRoundState.get_mvp` / `calculate_mvp`, `accuracy_pct` via `PlayerRoundState.get_accuracy`). The pure module never sees a Django model — only plain dicts.

**Ownership scope (UXP-14).** Benchmarks are **per Account**, not global: the population is the Rounds `owned_game_round_q(user)` admits — the Account's own plus **Unmanaged** Rounds, the same visibility as the rest of the Sandbox ([ADR-0038](../../docs/adr/0038-accounts-and-uniform-manager-ownership.md)). Another Account's Rounds never feed the numbers, on the HTML page, the API or the career overlay. `user` is a **required keyword** on `build_role_benchmarks`, `build_career_stats`, `get_all_benchmark_data`, `get_role_benchmark_samples` and `compute_benchmarks_uncached` (no caller can silently fall back to a global scan); an anonymous / `None` user sees Unmanaged Rounds only. Tests: `teams/tests/test_role_benchmarks_ownership.py`.

**Cache helper.** `teams/role_benchmarks_cache.py` exposes `get_all_benchmark_data(*, user)`, `get_role_benchmark_samples(role, stat, *, user)`, and `invalidate_role_benchmarks()`. Backing store is the Django cache framework keyed by a global version int: `role_benchmark_version` holds the int; `role_benchmark:v{version}:{scope}:{role}:{stat}` holds per-`(role, stat)` raw samples, where `{scope}` is `u{account_pk}` or `unmanaged` (UXP-14), so one Account's cached cells are never served to another. The version stays global, so any write busts every scope. A **single full-table scan on miss** populates every `(role, stat)` key for all 5 roles × 12 stats in one pass — second request for any cell post-invalidation is a hit (via `cache.get_many`, one round-trip for all 65 keys). Cached samples are **threshold-independent**: `apply_threshold` runs per request against the cached raw populations, so toggling `?threshold=` does not bust the cache. Invalidation is performed exclusively via `invalidate_role_benchmarks()` (which schedules the version bump under `transaction.on_commit` so a pre-commit reader can't repopulate the cache with not-yet-committed-stale data, then bumps `role_benchmark_version`), never by deleting individual keys. **Cache-miss cost scales with the Account's visible `PlayerRoundState` row count, not the requesting player** — the first `/players/<id>/stats/` or `/players/benchmarks/` request per Account after any write triggers a scan to repopulate that Account's cells; subsequent reads under the same version are cache-only.

**Signal handler + simulator hook.** `teams/signals.py::_bump_role_benchmark_version` registers `post_save` + `post_delete` on `PlayerRoundState` and calls `invalidate_role_benchmarks()` on every save / delete. **Crucially**, `BatchSimulator._flush_to_db` writes via `bulk_create`, which **does not fire `post_save`**, so the signal alone would miss every batch-simulated round — the simulator therefore performs a one-line **lazy-import** call to `invalidate_role_benchmarks()` immediately before its final return. The lazy import inside `_flush_to_db` avoids any `teams ↔ matches` circular-import risk; this is the **only** simulator change for HX-02 and it does not touch any simulation mechanic.

**Template surface.** NEW `templates/teams/role_benchmarks.html` (DOM ids `benchmark-filter-form`, `benchmark-threshold-input`, `benchmark-display-toggle`, `benchmark-table-{role}` ×5, `benchmark-row-{role}-{stat}`, `benchmark-no-data-notice`) and EXTENDED `templates/teams/player_career_stats.html` (new cells `benchmark-{role}-{stat_key}-{mean|median|delta|percentile|n}`, class `benchmark-na` for stats not in `STAT_KEYS`, anchor `role-benchmarks-link` pointing at `/players/benchmarks/`). The standalone page emits one `<table id="benchmark-table-{role}">` per role; each row id is `benchmark-row-{role}-{stat}` and contains 6 cells (mean/median/p25/p75/p90/n). The display toggle (`?display=mean`/`median`) swaps which of mean/median sits in the leading delta-target column.

**Empty-population UX.** `n=0` cells render `—` + `n = 0` (so the substring `n = 0` is greppable for tests). Below-threshold subject cells render `— (need N+ rounds)` substituting the active `threshold`. The standalone page emits `<div id="benchmark-no-data-notice">` when **every** `(role, stat)` returns `n=0` after the threshold. **UXP-14:** with `threshold > 0` it names the real gate and the active value — *"No benchmarks yet: a player needs at least N saved Round(s) in a role to count. ## LG-00 generation

Bulk player/team generation surface at `GET /teams/generate/` (URL name `generate_players`, view `teams/views.py::generate_players`, form `teams/forms.py::GenerateLeagueForm`). Two output modes selected by the form's `num_teams` dropdown: `num_teams ≥ 1` creates new **Teams** with auto-filled 6-slot rosters + optional bench when `players_per_team > 6`; `num_teams == "0"` creates a flat free-agent pool of 12–100 players on the reserved **Free Agents Team** (GLOSSARY.md — magic name `"Free Agents"`, no `is_system` field, no model change, no migration). **Pure generation module.** `teams/player_generator.py` is the algorithmic seam — **pure Python, no Django imports, no ORM, no settings access, no I/O, no global RNG** (frozen import allowlist: `random` for `Random` type-hint only with the RNG **injected** by the caller, `typing` for annotations, optional `collections`). The "no Django imports leaked" defensive check mirrors the RES-04 / RV-03 / HX-01 / HX-02 / HX-03 / HX-04 precedent. The module's public surface is three functions:

- `draw_stats(rng: random.Random, mean: float, std_dev: float) -> dict[str, int]` — returns a dict with **exactly 19 keys** in the module-level `_STAT_FIELDS` canonical order (3 awareness + 1 decision + 5 physical + 2 team + 8 role); each value is `max(0, min(100, round(rng.gauss(mean, std_dev))))`. Draws are made in `_STAT_FIELDS` order to keep RNG consumption deterministic given a seeded `random.Random`. The module does **not** range-check `mean` / `std_dev` — that is the form's job.
- `draw_preferred_roles(rng) -> list[str]` — returns 1–3 unique role names drawn from the module-local `_ROLE_NAMES` tuple `("commander", "heavy", "scout", "medic", "ammo")` with a `70 / 20 / 10` count distribution. Implementation pin (so tests can assert RNG-consumption parity): `n = rng.choices([1, 2, 3], weights=[70, 20, 10], k=1)[0]` then `rng.sample(_ROLE_NAMES, n)`.
- `assign_slots(preferred_roles_per_player) -> dict[str, int | None]` — deterministic greedy bipartite match of the first 6 players to the 6-slot `_SLOT_KEYS` tuple `("commander", "heavy", "scout_1", "scout_2", "medic", "ammo")`. Canonical-slot-first iteration; the slot's role is the key with any trailing `"_1"` / `"_2"` stripped (so both Scout slots want `"scout"`); lowest-unassigned-player-index tie-break (pinned by `test_assign_slots_deterministic_tiebreak`); unmatched slots receive `None` and the view back-fills them with leftover players in ascending player-index order. **Pure: no `random` calls inside `assign_slots`** — the function is deterministic given its input; the RNG enters at the level above when the view shuffles player order before assembling the input.

**`_STAT_FIELDS` canonical order (frozen, 19 entries).** `player_awareness, game_awareness, resource_awareness, decision_making, positioning, stamina, speed, flexibility, adaptability, communication, teamwork, Offensive_synergy, defensive_synergy, midfield_synergy, resupply_synergy, resupply_efficiency, accuracy, survival, special_usage`. **`Offensive_synergy` is intentionally capital-O** — the existing field name on `Player` in `teams/models.py` uses that casing and the view's `Player(**stats)` splat requires the keys to match the field names byte-for-byte. ## CRE-02 tiered generation

Adds the **League spread** ramp (GLOSSARY.md — **Even** / **Tiered** / **Steep**) to the LG-00 generation seam, so a create-League run can draw each competitive **Team** from *its own* stat mean instead of drawing all N teams from one distribution. The selector itself lives on the matches side (`CreateLeagueForm.league_spread`, Advanced create form only — see the **CRE-02 league spread** subsection in [`docs/agents/matches/league-lifecycle.md`](../../docs/agents/matches/league-lifecycle.md)); this app owns the arithmetic and the generation call. **The tier a Team was drawn from is a generation INPUT ONLY** — it is never persisted, never queried, never surfaced, so nothing here adds a model field or a migration and the League keeps exactly one ordering after generation (the measured strength rank). Seam contract: [`.claude/worktrees/cre-02-seam-contract.md`](../../.claude/worktrees/cre-02-seam-contract.md).

**Pure module additions — `teams/player_generator.py`.** CRE-02 only **adds** to the LG-00 surface; `draw_stats` / `draw_preferred_roles` / `assign_slots` and `_STAT_FIELDS` / `_ROLE_NAMES` / `_SLOT_KEYS` are zero-diff, and the new code stays inside the frozen import allowlist so `TestNoDjangoImportsLeaked` still covers the module.

- `LEAGUE_SPREAD_DELTAS: dict[str, float] = {"even": 0.0, "tiered": 8.0, "steep": 16.0}` — exactly three keys, exactly these lowercase tokens, exactly these float values. The tokens are the same strings the form's `league_spread` `ChoiceField` accepts, so a `cleaned_data` value indexes the dict directly.
- `compute_tier_means(num_teams: int, mean: float, delta: float) -> list[float]` — the linear, **mean-preserving** tier ramp. Returns a list of length `num_teams` where entry `i` is the stat mean the `i`-th generated Team's players are drawn from, index 0 the strongest tier and index `num_teams - 1` the weakest: `tier_mean(i) = clamp(mean + delta - 2 * delta * i / (num_teams - 1), 0.0, 100.0)`. Every entry is a `float` in `[0.0, 100.0]` and the list is monotonically **non-increasing** (strictly decreasing when `delta > 0` and no clamping is in play). **Degenerate cases** — `delta == 0` **or** `num_teams < 2` — return `[float(mean)] * num_teams`, which doubles as the `n - 1` divide-by-zero guard (so `num_teams == 0` ⇒ `[]` and `num_teams == 1` ⇒ `[float(mean)]`). **PURE:** no RNG, no I/O, no Django, deterministic given its three arguments — no seeding needed to test it.

**Mean preservation and its one caveat.** The ramp is symmetric about `mean`, so the *tier vector's* average equals `mean` exactly (`compute_tier_means(8, 50, 8)` runs 58.0 → 42.0 with a 16.0 head-to-tail gap and a list mean of exactly 50.0; `compute_tier_means(8, 50, 16)` runs 66.0 → 34.0, gap 32.0, list mean exactly 50.0). That is why a spread causes **no simulated-scoring drift and no Score Calibration re-baseline**. **The clamp is applied AFTER the ramp**, so mean preservation holds only where the ramp stays inside `[0, 100]` — at `mean=95, delta=16, num_teams=8` the head flattens at `100.0` and the list mean exceeds 95; at `mean=5, delta=16, num_teams=8` the tail flattens at `0.0` and the list mean exceeds 5. In clamped parameter ranges assert **bounds and monotonicity**, never mean preservation. Note also that the ramp preserves the mean of the *tier vector*, not the empirical mean of a finite random sample of generated Players.

**Generation call — `teams/views.py::_generate_teams`.** The helper gains one **additive keyword-only** parameter appended last, after `player_names_pool`: `tier_means: list[float] | None = None`. The return shape is unchanged (`list[Team]`, length `num_teams`, in creation order).

- `tier_means=None` (the default) is **byte-identical to pre-CRE-02 generation** — every Player of every Team is built with `_build_player_kwargs(rng, mean, std_dev)` exactly as before, with identical RNG consumption and identical outputs for a given seeded `rng`. Even passes `None`, **not** an all-equal list, which is what makes the default path a true no-op.
- A `list[float]` of length `num_teams` makes the Team at 0-based creation index `i` draw **all** its players — bench players 7+ included — with `_build_player_kwargs(rng, tier_means[i], std_dev)`; the `mean` parameter is then unused for those draws. The index-to-team mapping is locked: `tier_means[0]` belongs to the **first** Team created and `tier_means[num_teams - 1]` to the last. Nothing else about the loop moves — name popping, `Team.objects.create`, `Player.objects.create`, `_assign_team_slots`, `team.save()` and the append to `created_teams` keep their order, so per-player RNG consumption is unchanged.
- A list whose length `!= num_teams` **raises `ValueError`** (locked message: `f"tier_means has {len(tier_means)} entries but num_teams is {num_teams}"`), guarded at the top of the function **before the loop and before any ORM write**, so a mismatch creates zero Teams and zero Players. Silent tolerance was rejected: it would let a `num_teams` / `tier_means` drift ship a mis-tiered League undetected.

`_build_player_kwargs(rng: random.Random, mean: float, std_dev: int) -> dict` has its `mean` hint widened `int` → `float` (**its only change** — the body is untouched), because `compute_tier_means` returns `list[float]` and the downstream `draw_stats(rng, mean: float, std_dev: float)` already typed `mean` as `float`; the `int` annotation was the one dishonest link. `std_dev` stays `int`. Passing an `int` where `float` is annotated is valid under the PEP 484 numeric tower, so the three existing int-mean call sites need no edit — the keyword-only default likewise keeps `generate_players` and the Tournament create path (`matches/tournament_services/create.py` since ANG-01f) source-compatible, and only `matches.league_views._create_league_and_season` passes `tier_means=`.

**Determinism / scope.** `compute_tier_means` is pure and deterministic; `_generate_teams` still takes its RNG injected, and the extreme-tier draws stay in range because `draw_stats`'s existing `max(0, min(100, ...))` clamp still applies per stat. **Out of scope (deliberate):** the free-agent pool — `_generate_free_agents` is untouched and still draws at the flat `mean` (the spread is the N competitive Teams only); `_assign_team_slots` (slot assignment is tier-independent); any model field, any migration, any persisted or queryable "projected finishing order"; any re-application at the `next_season` rollover (create-time only — **LG-04 development** owns Team strength thereafter); and any simulation / Score Calibration interaction. Tests: `TestComputeTierMeans` is **appended** to the existing `teams/tests/test_player_generator.py`, and the DB-level `_generate_teams(tier_means=...)` coverage lives in the NEW `teams/tests/test_generate_teams_tiered.py` (`TestGenerateTeamsTierMeans`), which injects `rng=random.Random(42)` and asserts a direction/magnitude gap between `created_teams[0]` and `created_teams[-1]` — **the return list's creation order, never a persisted ranking** — rather than an exact point total.

Locked names — module constant `teams.player_generator.LEAGUE_SPREAD_DELTAS` (`{"even": 0.0, "tiered": 8.0, "steep": 16.0}`); pure function `teams.player_generator.compute_tier_means(num_teams, mean, delta) -> list[float]`; `teams.views._generate_teams(..., tier_means: list[float] | None = None)` (keyword-only, appended last, `ValueError` on length mismatch); widened hint `teams.views._build_player_kwargs(rng, mean: float, std_dev: int) -> dict`; test files `teams/tests/test_player_generator.py` (append `TestComputeTierMeans` only) + `teams/tests/test_generate_teams_tiered.py` (`TestGenerateTeamsTierMeans`). Pinned by the seam contract at [`.claude/worktrees/cre-02-seam-contract.md`](../../.claude/worktrees/cre-02-seam-contract.md).

Both `path(...)` entries are appended to `teams/urls.py` **above** the existing `<int:team_id>/` capture-group routes so the literal `import/` segment is unambiguous. Tests reverse via `reverse("import_roster")` and `reverse("import_roster_template")` — no `app_name:` prefix (consistent with the existing `teams/urls.py` pattern). Entry point is a single `"Import Roster"` anchor (DOM id `roster-import-link`) added to `templates/teams/team_list.html` between the LG-00 `generate-players-link` and the existing `Create New Team` button.

**Pure parsing module.** `teams/roster_importer.py` is the algorithmic seam — **pure Python, no Django imports, no ORM, no settings access, no I/O** (frozen import allowlist: `csv` + `io` + `dataclasses` + `typing` from stdlib only; **explicitly forbidden**: `django.*`, `teams.models`, `teams.forms`, `teams.views`, `teams.constants`, `teams.player_generator`, `matches.*`, and any I/O / `os.path` module). The "no Django imports leaked" defensive check mirrors the RES-04 / RV-03 / HX-01 / HX-02 / LG-00 precedent. The module's public surface is one function plus four dataclasses/exception:

- `parse_roster_csv(text: str) -> ParsedRoster` — single string argument, no `**kwargs`, no optional flags. Caller owns file reading + decoding; the function defensively strips a single leading `"﻿"` BOM before invoking `csv.DictReader` (belt-and-suspenders with the form's `utf-8-sig` decode). Header-level errors raise `RosterImportError` IMMEDIATELY without attempting per-row parsing; per-row coercion errors accumulate across the whole file and bundle into a single raise after the loop plus an extra in-file collision pass; on success returns `ParsedRoster` (coercion-valid + in-file-collision-free).
- `ParsedRow(row_num, team, name, role, profile, stats, preferred_roles)` — `frozen=True` dataclass. `profile` is a 5-key dict (`age, started_playing_age, total_games, home_site, height`) whose keys MUST match `Player` field names byte-for-byte so the view's `Player.objects.create(**row.profile, **row.stats)` splat lands. `stats` always carries all 19 `STAT_COLUMNS` keys, defaulted to `STAT_DEFAULT` (`50`) where the cell was blank or the column absent. `preferred_roles` is 0–5 unique lowercase role names.
- `ParsedRoster(rows, by_team)` — `frozen=True` dataclass. `rows` is the flat CSV-order list (used for diagnostics + raw iteration); `by_team` is the view's primary consumption shape, a `dict[str, list[ParsedRow]]` whose insertion order matches first-appearance order of each team in the file (Python 3.7+ dict insertion-order guarantee — locked).
- `RowError(row_num: int, field: str | None, message: str)` — `frozen=True` dataclass, hashable so tests may put them in sets. `row_num` is **1-based DATA row index**: the first data row (line 2 of the file) is `row_num=1`; the header is line 1; file-level errors use `row_num=0` so the template sorts errors top-to-bottom with file-level first. `field` is `None` only for whole-row or whole-file errors.
- `RosterImportError(Exception)` with constructor `__init__(self, errors: list[RowError])` exposing `.errors`. The view re-renders this list verbatim and may **extend** it with DB-level slot collisions detected during the pre-flight check before re-raising.

**Module constants (frozen, hand-rolled locally — no import from `player_generator`).** `ROLE_NAMES = ("commander", "heavy", "scout", "medic", "ammo")`; `SLOT_LIMITS = {"commander": 1, "heavy": 1, "scout": 2, "medic": 1, "ammo": 1}`; `STAT_COLUMNS` is the 19-tuple matching `teams/player_generator.py::_STAT_FIELDS` verbatim — including the **intentional capital-O** `Offensive_synergy` so the view's `Player(**stats)` splat lands on the matching field — pinned by `test_stat_columns_equals_player_generator_stat_fields` (the ONE allowed `teams.player_generator` import inside the pure-unit test file); `REQUIRED_COLUMNS` is the 8-tuple `("team", "name", "role", "age", "started_playing_age", "total_games", "home_site", "height")`; `OPTIONAL_COLUMNS = ("preferred_roles", *STAT_COLUMNS)` (20 entries); `ALL_COLUMNS = (*REQUIRED_COLUMNS, *OPTIONAL_COLUMNS)` (28 entries — the declared order that drives the template-CSV header row); `PROFILE_BOUNDS = {"age": (5, 100), "started_playing_age": (3, 100), "total_games": (0, 100_000)}`; numeric constants `STAT_DEFAULT = 50`, `STAT_MIN = 0`, `STAT_MAX = 100`, `MAX_DATA_ROWS = 1000`, `NAME_MAX_LEN = 100`, `TEAM_NAME_MAX_LEN = 100`, `HOME_SITE_MAX_LEN = 100`, `HEIGHT_MAX_LEN = 20`.

**Coercion + error policy.** Per-cell rules: `team` / `name` stripped + non-empty + ≤100 chars; `role` lowercased + stripped + must be in `ROLE_NAMES` (so `"COMMANDER"` succeeds and lowercases); the three int profile fields use `int()` + `PROFILE_BOUNDS`; `home_site` / `height` stripped strings, empty allowed (becomes `""`); `preferred_roles` split on `","` + each entry stripped + lowercased + each non-empty entry in `ROLE_NAMES` + no duplicates within the cell (empty cell or column absent → `[]`); each of the 19 stat columns: cell omitted / blank / column absent → `STAT_DEFAULT`, else `int()` bounded `[STAT_MIN, STAT_MAX]`. **Header-level errors** (missing required column, unknown column, duplicate column, > `MAX_DATA_ROWS` data rows) raise `RosterImportError` IMMEDIATELY with `row_num=0` and skip per-row parsing — there is no point reading rows under a bad header. **Per-row coercion errors** accumulate across the whole file (no per-row early return) and are joined by an **in-file collision pass** that emits four hard-reject categories before the single bundled raise: duplicate `(team, name)` pair (`field="name"`), > 1 row of any non-Scout role on the same team (`field="role"`, message contains `"Too many"`, fires on the 2nd occurrence), > 2 Scouts on the same team (`field="role"`, fires on the 3rd occurrence), and slot-overflow detected by the view's DB pre-flight pass against pre-existing Teams (appended to the same `RosterImportError.errors` before any write — see view section below).

## LG-00c sortable players tab

Read-only, server-side-sort, paginated index of every Player (including the Free Agents pool — no special-case exclusion) at `GET /players/` (URL name `player_list`, view `teams/views.py::player_list`, template `templates/teams/player_list.html`). Three query params drive presentation: `?sort=<key>` (default `"team"`, 23 accepted keys), `?dir=<asc|desc>` (default `"asc"`, case-sensitive — `"ASC"` falls back to `"asc"`), and `?page=<int>` (default 1, `EmptyPage` / `PageNotAnInteger` → page 1). Invalid params never raise — every bad input is coerced to a default by the two forgiving-fallback helpers (HX-02 pattern), and `get_object_or_404` is not used (the view never 404s).

**URL include.** One new `path("", views.player_list, name="player_list")` is appended to `teams/player_urls.py` **after** the two existing entries — final order is `benchmarks/` → `<int:player_id>/stats/` → `""`. The trailing position is mandatory: the `<int:player_id>` capture group cannot match an empty path segment, but the explicit ordering pin prevents a future regex change from silently shadowing the new route. Reverse via the bare `reverse("player_list")` — no `app_name:` prefix, consistent with the existing HX-01 / HX-02 routes in the same file. The outer `path("players/", include("teams.player_urls"))` mount in `laserforce_simulator/urls.py` is reused unchanged.

**No new pure-aggregation module.** LG-00c **deliberately ships no `teams/*.py` aggregation seam** — the helpers and constants live inline at module scope in `teams/views.py`, contrasting with HX-01 (`teams/career_stats.py`), HX-02 (`teams/role_benchmarks.py`), LG-00 (`teams/player_generator.py`), and LG-00b (`teams/roster_importer.py`) which all ship a pure module. The test file imports `_coerce_sort`, `_coerce_dir`, `_SORT_KEYS`, `_SORT_KEYS_DISPLAY`, `_VALID_DIRS`, and `_PAGE_SIZE` directly from `teams.views`. The helper unit tests (`TestCoerceSortAndDir`) run under Django's `TestCase` runner because of the `teams.views` import — they are NOT pure-unit in the HX-01 / HX-02 sense (those have actual Django-free pure modules with `test_no_django_imports_leaked` defensive checks; LG-00c does not).

**Sort whitelist — 23 accepted keys total.** Four new module-level constants in `teams/views.py`, placed beside the existing HX-02 `_coerce_threshold` / `_coerce_display`. `_SORT_KEYS: dict[str, str]` is a **22-entry** dict literal (URL key → ORM target) — the 19 stat fields plus `name` / `team` / `overall_rating`; insertion order is declared order for clarity, tests treat membership not ordering. `_SORT_KEYS_DISPLAY: tuple[tuple[str, str], ...]` is the **23-entry** display tuple (the 22 ORM-backed keys PLUS the `preferred_roles` sentinel — that's how the template iterates the column order including the JSON-field column) in the locked display order `(name, team, preferred_roles, overall_rating, player_awareness, game_awareness, resource_awareness, decision_making, positioning, stamina, speed, flexibility, adaptability, communication, teamwork, offensive_synergy, defensive_synergy, midfield_synergy, resupply_synergy, resupply_efficiency, accuracy, survival, special_usage)` paired with human labels `(Name, Team, Preferred Roles, Overall, Player Aware, Game Aware, Resource Aware, Decision, Positioning, Stamina, Speed, Flexibility, Adaptability, Communication, Teamwork, Offensive Syn, Defensive Syn, Midfield Syn, Resupply Syn, Resupply Eff, Accuracy, Survival, Special Usage)`. `_VALID_DIRS = ("asc", "desc")` and `_PAGE_SIZE = 50` round out the constants.

**Capital-O `Offensive_synergy` casing quirk.** URL key `offensive_synergy` (lowercase alias) maps to ORM target `Offensive_synergy` (capital-O, matching the existing `Player.Offensive_synergy` field byte-for-byte and the `_STAT_FIELDS` / `STAT_COLUMNS` precedent set by LG-00 / LG-00b). Pinned by `test_sort_by_offensive_synergy_url_alias_maps_to_capital_O_field` — the test creates 3 Players with distinct `Offensive_synergy` values, GETs `?sort=offensive_synergy&dir=desc` with the lowercase URL key, and asserts the top row is the highest-value player.

**`preferred_roles` Python-side sentinel — the 23rd accepted key.** `"preferred_roles"` is NOT in `_SORT_KEYS` (the field is a JSON list with no ORM target). The view handles it in a separate branch: materialise via `rows = list(qs)`, then `rows.sort(key=lambda p: (",".join(p.preferred_roles or []), p.name), reverse=(direction == "desc"))`, then `Paginator(rows, _PAGE_SIZE)`. Empty `preferred_roles` joins to `""` which sorts to the **TOP** of asc (`""` is lexicographically less than any non-empty string); the secondary `player.name` component is the deterministic tiebreak. Pinned by `test_sort_by_preferred_roles_python_branch` — the test creates 3 Players with `preferred_roles` = `[]`, `["scout"]`, `["commander", "heavy"]` and GETs `?sort=preferred_roles&dir=asc`, asserting the empty-list player sorts first, then `"commander,heavy"`, then `"scout"`.

**Forgiving-fallback helpers (inline, mirror HX-02).** Two new module-level functions at the same scope as `_coerce_threshold` / `_coerce_display`. `_coerce_sort(raw: str | None, default: str = "team") -> str` returns `raw` if `raw in _SORT_KEYS or raw == "preferred_roles"`, else `default` — the accepted-key set is the union of `_SORT_KEYS` keys and the `preferred_roles` sentinel (inlined, not exposed as a module-level constant). `_coerce_dir(raw: str | None, default: str = "asc") -> str` returns `raw` if `raw in _VALID_DIRS`, else `default` — case-sensitive (so `"ASC"` falls back to `"asc"`, mirroring `_coerce_display`'s casing discipline). Both helpers return `str` (never `None`); tests pin direct-call behaviour (`TestCoerceSortAndDir`).

**View.** `player_list(request)` is undecorated, runs `_coerce_sort(request.GET.get("sort"))` and `_coerce_dir(request.GET.get("dir"))`, builds the queryset via `Player.objects.select_related("team").annotate(overall_rating_db=...)` where the annotation is `(sum of 19 F-fields) / 19.0` (using `F("Offensive_synergy")` with the capital-O to match the field; the `/ 19.0` ensures float semantics under the SQL backend). The Python branch (`sort == "preferred_roles"`) materialises and sorts in memory as described above. `Paginator(qs_or_rows, _PAGE_SIZE)` handles pagination; `EmptyPage` / `PageNotAnInteger` fall back to page 1. The view assembles two URL-encoded helper strings via `request.GET.copy()` + `.pop()`: `querystring_without_page` (used by Previous / Next page links so sort + dir survive page navigation) and `querystring_without_sort_dir_page` (used by column-header `<a>` hrefs so clicking a header drops `page=` and resets to page 1). Context ships **exactly seven** frozen keys: `page_obj, paginator, sort, dir, sort_keys, querystring_without_page, querystring_without_sort_dir_page`. The ORM branch issues exactly one queryset materialisation (the `Paginator` `.count()` + `.page()` round-trips are part of the paginator contract); the Python branch materialises once via `list(qs)`.
